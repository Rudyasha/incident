# Архитектура и flow

## 1. Путь бизнес-операции

```mermaid
flowchart TD
    M[Водитель / Driver App] -->|POST /api/v1/exchanges| A[Lincore API]
    A -->|Сохранить обмен| D[(База Lincore)]
    A -->|Опубликовать событие| K[Kafka: lincore.orders]
    A -.->|HTTP-ответ| M
    K --> C[1C Connector]
    C -->|Создать счёт| E[1С:ERP]
    E --> I[Счёт клиента]
```

HTTP-ответ описывает результат запроса к API. Создание счёта идёт асинхронно. Что именно означает статус «Завершено», необходимо закрепить в контракте.

## 2. Последовательность инцидента

Схема реконструирована из переписки. Она показывает порядок событий; место потери ответа не установлено.

```mermaid
sequenceDiagram
    autonumber
    participant App as Driver App
    participant API as Lincore API
    participant DB as База
    participant K as Kafka
    participant C as Connector
    participant ERP as 1С:ERP
    App->>API: POST exchange_id=X
    API->>DB: Сохранить, id=318274
    DB-->>API: COMMIT
    API->>K: Событие X, offset=88234
    API--xApp: Успешный ответ не получен клиентом
    Note over App: Timeout, точка «В работе»
    K->>C: Сообщение 88234
    C->>ERP: Создать счёт для X
    ERP-->>C: Invoice created OK, inv-2026-00088234
    App->>API: Повторный POST, тот же X
    API->>DB: Вторая запись, id=318275
    API->>K: Второе событие, offset=88235
    API-->>App: 200 OK
    K->>C: Сообщение 88235
    C->>ERP: Повторно создать счёт для X
    ERP-->>C: 400 duplicate_document
    C->>K: Перенос второго сообщения в DLQ
```

## 3. Где возникает расхождение

```mermaid
flowchart TD
    X[Операция exchange_id=X] --> A[После первой попытки]
    X --> B[После повторной попытки]
    A --> M[Mobile: сохранение не подтверждено]
    A --> D[API: обмен сохранён]
    A --> I[Connector: счёт создан успешно]
    B --> E[Второе событие: duplicate_document]
    E --> Q[DLQ]
    Q -.->|Возможная связь, нужно проверить| R[Реестр: invoice=N/A]
```

Пунктиром отмечена **гипотеза**, а не доказанная зависимость. Состояния первой и второй попытки разделены: нельзя показывать поздний реестр и ранний UI как один синхронный снимок.

## 4. Предлагаемый безопасный повтор

Это вариант ожидаемого поведения для согласования с аналитиком.

```mermaid
flowchart TD
    T[Timeout: результат неизвестен] --> G[Проверить состояние операции по X]
    G --> F{Результат проверки}
    F -->|Сохранена| S[Восстановить статус обмена]
    F -->|Не найдена| P[Повторить идемпотентный POST с X]
    F -->|Проверка недоступна| W[Оставить pending, повторить с backoff]
    P --> V{Ключ уже существует?}
    V -->|Нет| N[Атомарно сохранить операцию и outbox]
    V -->|Да, данные совпадают| O[Вернуть существующий результат]
    V -->|Да, данные отличаются| C[Явный конфликт, без перезаписи]
```

Ответ «не найдена» не устраняет гонку с незавершённым первым запросом. Поэтому безопасность обеспечивает серверная идемпотентность, даже при предварительной проверке состояния.
