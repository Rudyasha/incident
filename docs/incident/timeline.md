# Хронология и корреляция

Время и идентификаторы перенесены из переписки; точность до секунды не означает сверку исходного лога.

## Последовательность

| Время | Компонент | Событие | Значение для расследования |
|---|---|---|---|
| 14:03:02 | Mobile | Первый POST для X | Начало первой попытки |
| 14:03:06 | API / DB | COMMIT, запись 318274 | Сохранение предшествует timeout |
| 14:03:06 | API / Kafka | Публикация 88234; сформирован 200 | Ответ не подтверждает получение клиентом |
| 14:03:32 | Mobile | Timeout | Результат для клиента неизвестен |
| 14:03:35 | Connector | Получено 88234 | Первое событие дошло до интеграции |
| 14:03:38 | 1С / Connector | `Invoice created OK` | Есть свидетельство создания счёта |
| 14:04:05 | Mobile / API | Повтор X; запись 318275; событие 88235 | Одна операция обработана повторно |
| 14:04:07 | Connector | Получено 88235 | Началась вторая обработка |
| 14:04:09 | 1С / Connector | `duplicate_document`, затем DLQ | Ошибка относится ко второй попытке |
| Конец дня | Реестр | `invoice=N/A` | Нужно установить алгоритм формирования статуса |

**Ключевое наблюдение:** сообщение об успешном создании счёта появляется до повторного запроса водителя.

## Карта корреляции

| Признак | Первая попытка | Повтор |
|---|---|---|
| Бизнес-ключ | `ex-20260824-0010482` | Тот же ключ |
| DB row | `318274` | `318275` |
| Kafka offset, по пересказу | `88234` | `88235` |
| Результат 1С | `inv-2026-00088234` | `duplicate_document` |
| Дальнейшая обработка | Успешный ответ | DLQ |

`exchange_id` связывает бизнес-операцию; `traceId` — отдельную техническую попытку. Для Kafka дополнительно нужны **topic + partition + offset**, consumer group и event ID. Одинаковый Kafka key сам по себе не удаляет дубли.

## Что ещё проверить во времени

- DB lock wait около 4,12 с может увеличить latency, но сам по себе не объясняет клиентский timeout около 30 с.
- Интервал публикация → получение первого события составляет около 29 с, второго — около 2 с. Проверить lag в момент инцидента и настройки consumer; это ещё не доказательство сбоя Kafka.
- `lag=0` в конце дня не доказывает успешность бизнес-обработки: сообщение могло уйти в DLQ и быть подтверждено consumer.
- Уточнить семантику timestamp: время возникновения события, записи лога или его доставки в систему наблюдаемости.
