# 3. Предварительное заключение

!!! abstract "Локализация"
    Основная версия — повторная обработка одной бизнес-команды после неопределённого результата первого HTTP-запроса. В тексте переписки есть признаки двух записей и двух Kafka-событий при одном `exchange_id`.

## Что, вероятнее всего, произошло

Первый запрос был сохранён Lincore и опубликован в Kafka, но клиент не получил подтверждения. Приложение оставило точку «В работе», после чего водитель повторил действие. Backend обработал тот же X повторно и создал ещё одну запись и событие.

Для первой попытки приведён ответ `Invoice created OK` с ID `inv-2026-00088234`. Для второй — `duplicate_document` и перенос в DLQ. Поэтому формулировка «счёт не сформирован в 1С» противоречит описанному успешному ответу первой обработки. Состояние документа необходимо проверить непосредственно в 1С.

Позднее реестр показывает `invoice=N/A`. Это отдельное расхождение, для которого нужно проверить связь счёта с обменом, правила проекции и последующие изменения документа. Причинная связь «DLQ перекрыла success» пока не доказана.

## Триггер, причина и влияние

| Категория | Вывод | Уверенность |
|---|---|---|
| Триггер повторной попытки | Клиент не получил подтверждения | Поддерживается пересказом логов |
| Основная техническая версия | Повтор X не сводится к ранее принятой операции | Высокая при совпадении payload и назначении записей БД |
| Поведение интеграции | Повторное создание завершилось ошибкой и DLQ | Описано в переписке; политика требует проверки |
| Механизм N/A | Возможная ошибка связи или вычисления итогового статуса | Гипотеза |
| Бизнес-влияние | Ошибочная/неполная отчётность и ручная обработка | Описано; масштаб и финансовый эффект не измерены |

## Что нужно для окончательного RCA

- Сверить значения и последовательность с исходными логами.
- Доказать, что два запроса — одна операция с одинаковыми данными.
- Проверить две бизнес-записи и соответствующие публикации.
- Найти документ в 1С, проверить его данные и историю.
- Воспроизвести вычисление `invoice=N/A` для этой операции.
- Согласовать ожидаемую семантику повторов и закрепить её проверками.

## Приоритетные действия

**Восстановление:** сверить существующий документ с X и восстановить корректную связь в реестре по согласованной процедуре. Повторная обработка DLQ должна учитывать уже существующий счёт.

**Предотвращение:** атомарная защита уникальности бизнес-операции; определённый ответ на совпадающий повтор и конфликтующий payload; идемпотентная обработка на границе Connector → 1С.

**Надёжность доставки:** оценить transactional outbox, сохраняющий обмен и намерение публикации в одной транзакции. Publisher всё ещё может доставлять событие повторно — consumer должен это выдерживать. Разрыв DB/Kafka является риском, а не установленной причиной данного инцидента.

**Наблюдаемость:** сквозная связь exchange ID → attempts → events → invoice; метрики повторов, pending billing, DLQ и расхождений реестра с 1С. Порог и срок восстановления согласуются с владельцем процесса.
