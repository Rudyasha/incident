# 1. Гипотезы по слоям

Статусы ниже отражают согласованность с **текстом переписки**. Подтверждение по оригинальным артефактам ещё не выполнено.

| ID | Слой | Гипотеза | Текущая оценка |
|---|---|---|---|
| H1 | Клиент | После timeout клиент повторяет ту же команду | Поддерживается описанной последовательностью |
| H2 | Сеть | Успешный ответ не дошёл до приложения | Результат неизвестен; точное место сбоя не установлено |
| H3 | Backend | Повтор X создаёт новую операцию | Основная версия при совпадении payload |
| H4 | База | Ожидание блокировки увеличило задержку | Сопутствующий фактор, не доказанная причина timeout |
| H5 | Kafka | API опубликовал два события одной операции | Поддерживается связью с двумя HTTP-попытками |
| H6 | Интеграция 1С | Повтор трактуется как ошибка без сверки документа | DLQ наблюдается; корректность политики требует контракта |
| H7 | Отчётность | Ошибка повтора перекрыла успех первой обработки | Не подтверждено; нужен алгоритм реестра |
| H8 | Данные | Ключ на основе даты и клиента допускает коллизию | Риск требований; альтернативное объяснение дубля |

## H1 · Клиент не восстанавливает результат после timeout

**Основание:** ошибка сохранения, статус «В работе» и повтор того же X. Ошибка HTTP-клиента не доказывает откат на сервере.

**Проверю:** сохранение X и payload между попытками; сетевые ретраи библиотеки; действия водителя; локальную очередь pending; запрос статуса; восстановление после background/foreground. Эти lifecycle-события не равны доказанному завершению процесса приложения.

**Критерий:** если приложение получает актуальное состояние сервера и всё равно отправляет новую команду, дефект локализуется в клиентской логике. Если повтор разрешён контрактом, основной вопрос — безопасность его серверной обработки.

## H2 · Ответ потерян или соединение закрыто

**Основание:** сервер завершил обработку, клиент зафиксировал timeout; в пересказе упомянуто закрытие соединения.

**Проверю:** access/error logs gateway, request ID, upstream status, времена отправки заголовков и тела, client disconnect, настройки timeout, смену сети и lifecycle приложения.

**Критерий:** связанная цепочка логов локализует разрыв между конкретными компонентами. По одной строке `200` нельзя доказать доставку ответа; по timeout нельзя утверждать, что у водителя пропал интернет.

## H3 · Backend не обеспечивает идемпотентность

**Основание:** две записи 318274/318275 и два события при одном X.

**Проверю:** фактические строки БД, назначение этих таблиц, полные payload, tenant/route/point, уникальные индексы, ветку обработки существующего ключа. Две строки могут быть журналом попыток — нужно доказать, что это именно два бизнес-объекта.

**Эксперимент:** отправить два одинаковых запроса последовательно, затем параллельно; отдельно оборвать получение первого ответа после COMMIT. Ожидание для согласованного идемпотентного контракта: один бизнес-объект и один финансовый результат. Повторная доставка события допустима, повторный бизнес-эффект — нет.

## H4 · Блокировка БД стала фактором задержки

**Основание:** в переписке указан lock wait 4120 ms.

**Проверю:** блокирующую транзакцию, тип lock, длительность транзакций, затронутые строки, connection pool, p95/p99 запросов и совпадение со всплеском ошибок.

**Ограничение:** этот интервал меньше клиентского timeout. Устранение блокировки может снизить частоту повторов, но не исправляет семантику повторного POST.

## H5 · Дублирование возникло до consumer

**Основание:** отдельные публикации после первого и второго HTTP-запроса. Это отличается от повторного чтения одного сообщения после сбоя consumer.

**Проверю:** topic, partition, offset, event ID, payload и producer trace для обеих записей, затем commits и retries consumer.

**Критерий:** две публикации одного бизнес-события связывают источник дубля с API. Повторное потребление одной записи локализует иной сценарий, который также требует идемпотентного consumer.

## H6 · Connector не разрешает ситуацию «документ уже существует»

**Основание:** второй вызов получает `duplicate_document` и уходит в DLQ.

**Проверю:** поиск существующего документа, связь с X, организацию, клиента, сумму, валюту, строки документа и текущий статус. Затем — договорённую классификацию ошибок и порядок ACK/commit после записи результата.

**Критерий:** совпадающий документ можно связать с операцией и считать повтор обработанным, если это согласовано контрактом. Несовпадающий документ — конфликт, требующий разбирательства. Любой `400` автоматически превращать в success нельзя.

## H7 · Реестр потерял связь с успешным счётом

**Основание:** успешный ответ интеграции и позднее `invoice=N/A`.

**Проверю:** источник данных отчёта, join по business ID или DB row ID, фильтры даты/организации/статуса, порядок событий, сохранённый invoice ID и приоритет error/success. Сопоставлю обе записи обмена с документом.

**Альтернативы:** реестр связан со второй строкой; успешное событие не записано в проекцию; документ позже отменён; фильтр исключил счёт; success перезаписан ошибкой. Без этих проверок нельзя утверждать, что именно DLQ вызвала N/A.

## H8 · Коллизия бизнес-идентификатора

**Основание:** описан формат `ex-{YYYYMMDD}-{client_id}`.

**Проверю:** допустимы ли два обслуживания клиента за день, как учитываются часовой пояс, организация и повторное посещение, когда генерируется и сохраняется ключ.

**Критерий:** если это две разные операции с одним X, простое подавление дубля потеряет законный обмен. Сначала согласуется идентичность операции, затем уникальность и идемпотентность.
