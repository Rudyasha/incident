# 2. Разбор артефактов A–C

Оригиналы не приложены. Ниже — конкретный план проверки и наблюдения, доступные через пересказ. Номера строк и страниц не выдумываются.

## A · Спецификация

| Что ищу | Почему важно | Результат проверки |
|---|---|---|
| Семантика `POST /api/v1/exchanges` и HTTP 200 | Нужно отделить принятие обмена от биллинга | Явный критерий успешности каждого этапа |
| Повтор с тем же X и тем же/другим payload | Без контракта нет надёжного ожидаемого результата | Replay существующего результата либо конфликт |
| Область уникальности X | Дата + клиент могут не различать два посещения | Правило идентичности бизнес-операции |
| Граница транзакции DB → Kafka | Возможен COMMIT без события | Механизм восстановления и тестируемые гарантии |
| Timeout, retries, pending, восстановление приложения | Timeout оставляет неопределённый результат | Правила повторов, лимиты и состояние UI |
| Ошибки 1С, DLQ, сверка и источник статуса | Необходимо разрешать расхождение систем | Таблица ошибок и правила reconciliation |

В переписке раздел идемпотентности описан как незавершённый. Это требует сверки с версией документа; наблюдаемое поведение и пробел требований фиксируются отдельно.

## B · Логи

### Порядок расследования

1. Зафиксировать окружение, дату, timezone, route/point/client и полный X.
2. Найти все HTTP-попытки X и сравнить значимую нагрузку. Trace ID каждой попытки хранить отдельно.
3. Для каждой попытки связать validation → transaction → COMMIT/ROLLBACK → publication → HTTP response/disconnect.
4. Сопоставить Kafka topic/partition/offset и payload с вызовом 1С.
5. Проверить ответ 1С, invoice ID и последующую фиксацию статуса в Connector.
6. Разобрать сообщение DLQ: исходное событие, причина, число попыток, timestamps, возможность безопасной повторной обработки.
7. Связать данные с конкретной строкой финансового реестра и проверить существующий документ в 1С.

### Что будет значимым признаком

| Признак | Что позволяет заключить | Чего не доказывает |
|---|---|---|
| COMMIT до timeout | Сервер мог завершить сохранение | Что клиент получил ответ |
| Две бизнес-записи с одним X | Возможное нарушение уникальности | Что payload одинаков и это не журнал попыток |
| Две публикации после двух POST | Возможный источник дубля на стороне API | Что Kafka сама продублировала запись |
| `Invoice created OK` + invoice ID | Интеграция сообщила об успехе | Что документ сейчас существует и соответствует операции |
| `duplicate_document` → DLQ | Вторая попытка завершилась ошибкой | Что исходный счёт отсутствует |
| `lag=0` | Нет отставания по конкретной измеренной метрике | Что нет DLQ и биллинг успешно завершён |

## C · Скриншот приложения

В переписке описаны точка 3, 8 чистых/8 грязных ковров, статус «В работе», ошибка сохранения и доступная кнопка завершения.

**Проверяю на оригинале:** точку, количества, точную формулировку сообщения, доступность кнопки и время снимка. Связываю снимок с логами той же попытки.

**Проверяю воспроизведением:** double tap, состояние кнопки во время запроса, timeout после COMMIT, восстановление экрана, сохранение X, background/foreground и отдельный сценарий kill/relaunch.

**Граница вывода:** скриншот показывает клиентский симптом. Он не доказывает отсутствие строки в БД, счёта в 1С или конкретную причину сетевой ошибки.

## Минимум данных для следующего шага

Полные A–C; payload двух запросов; строки БД и схема уникальности; Kafka metadata и события; карточка документа 1С; правила и данные построения финансового реестра. Эти данные позволяют подтвердить либо пересмотреть основную версию без догадок о реализации.
