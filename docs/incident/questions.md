# 4. Три вопроса системному аналитику

Каждый вопрос закрывает конкретный пробел и определяет проверяемый результат.

## 1 · Что делает повтор той же операции?

**Вопрос:** что является идентификатором одного обмена и как обрабатывается повторный `POST /api/v1/exchanges` с тем же ключом — последовательно, параллельно и после timeout? Какой ответ возвращается при одинаковом payload и при изменённых данных? Гарантирует ли формат ключа уникальность при нескольких посещениях клиента за день?

**Почему блокирует проверку:** без этого нельзя отличить безопасный retry от второго законного обмена и конфликта данных.

**Примеры для согласования:**

| Вход | Предлагаемое ожидание, требует согласования |
|---|---|
| X, clean=8; затем тот же X, clean=8 | Существующий результат, без нового бизнес-эффекта |
| X, clean=8; затем тот же X, clean=9 | Явный конфликт, без скрытой перезаписи |
| Два параллельных одинаковых запроса X | Один обмен; детерминированные ответы обоим клиентам |
| Второе самостоятельное посещение клиента | Отличимый бизнес-ключ новой операции |

Нужно также определить область ключа (например, организация), срок хранения результата и поведение при ещё выполняющемся первом запросе.

## 2 · Когда обмен считается завершённым?

**Вопрос:** «Завершено» означает сохранение обмена, публикацию события или подтверждённый биллинг? Как водитель видит неизвестный результат после timeout и как приложение восстанавливает состояние при следующем открытии?

**Почему блокирует проверку:** обмен может быть сохранён, а счёт ещё обрабатываться. Один статус без определения не даёт однозначного expected result.

**Что согласовать:** отдельно состояние обмена и биллинга; переходы pending/success/error; API проверки состояния; доступность повторного действия; интервалы повторов и допустимое время ожидания.

**Критерий:** для сценария «COMMIT успешен, ответ потерян, 1С временно недоступна» определены состояния API, приложения и биллинга на каждом этапе и после восстановления.

## 3 · Как определяется итоговый статус счёта?

**Вопрос:** какой источник является авторитетным при расхождении 1С и реестра? Что делать, если для X уже есть счёт, а повтор получил `duplicate_document` и ушёл в DLQ? Какие поля нужно сверить перед признанием повтора успешным?

**Почему блокирует проверку:** ошибка одной технической попытки не определяет автоматически итог всей бизнес-операции.

**Что согласовать:** критерии совпадения документа, связь с X, приоритет и порядок обновления статусов, ответственный за сверку, срок восстановления, правила обработки DLQ и аудит ручных изменений.

**Критерий:** совпадающий документ корректно связывается с обменом; конфликтующий документ не маскируется как success; реестр показывает результат по согласованному правилу даже при событиях, пришедших не по порядку.
