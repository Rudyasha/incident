# Задача 2. Баг-репорт

## Тайтл

Повторный `/api/v1/exchanges` с тем же `exchange_id` создаёт дубликат, после чего созданный счёт отображается как `invoice=N/A`.

| Серьёзность | Приоритет |
|---|---|
| Critical | P1 High |

## Окружение

```yaml
Компоненты:
  - Lincore Driver App, React Native
  - Lincore API
  - DB
  - "Kafka, topic: lincore.orders"
  - 1C Connector
  - 1C:ERP
  - финансовый реестр

Дата инцидента: 24.08.2026
Филиал: Москва-Север
Рейс: M-148
Точка: '3, "Кафе Утро"'
client_id: 10482
driver_id: drv-0042
exchange_id: ex-20260824-0010482
```

## Предусловия

1. Водитель авторизован.
2. Рейс назначен водителю и находится в статусе `В работе`.
3. Точка маршрута достигнута.
4. Ковры отсканированы.
5. Exchange ещё не завершён.

## Шаги воспроизведения

1. Открыть точку маршрута в статусе `В работе`, для которой выполнено сканирование ковров.
2. Нажать `Завершить обмен`.
3. Убедиться, что приложение отправило `POST /api/v1/exchanges` с новым уникальным `exchange_id`.
4. После того как запрос дошёл до backend и был успешно обработан, задержать или заблокировать HTTP response на время больше клиентского timeout.
5. Убедиться по backend logs, что:

    - exchange сохранён в БД;
    - Kafka-событие опубликовано.

6. Дождаться timeout в мобильном приложении.
7. Убедиться, что приложение показывает ошибку сохранения и оставляет точку в статусе `В работе`.
8. Повторно нажать `Завершить обмен`.
9. Убедиться, что повторный POST отправляется с тем же `exchange_id`.
10. Второй запрос и response пропустить без задержки.
11. Проверить:

    - записи в Lincore DB;
    - сообщения Kafka по `exchange_id`;
    - обработку сообщений 1C Connector;
    - документ в 1С;
    - итоговый статус в финансовом реестре.

### Примечание к воспроизведению

> При наличии тестового окружения я бы сначала минимизировала сценарий до уровня API и интеграции, чтобы исключить не относящиеся к дефекту UI. Для воспроизведения именно timeout использовала бы Charles или аналогичный инструмент.

## Фактический результат

Повторный запрос обрабатывается как новая операция.

Для одного `exchange_id` появляются две записи exchange:

```text
Первый запрос:
DB id = 318274

Повторный запрос:
DB id = 318275
```

И два Kafka-сообщения:

```text
offset = 88234
offset = 88235
```

Первое Kafka-сообщение успешно создаёт счёт в 1С:

```ini
invoice = inv-2026-00088234
amount = 4800 RUB
```

Повторное сообщение пытается создать документ с тем же номером и получает:

```text
400
Документ с номером ex-20260824-0010482 уже существует
```

После этого сообщение отправляется в DLQ с причиной:

```text
duplicate_document
```

В финансовом реестре итоговое состояние точки отображается как:

```text
invoice=N/A
Ошибка формирования счёта.
Требуется ручная обработка.
```

Несмотря на то, что счёт был успешно создан первым сообщением.

## Ожидаемый результат

- Новая запись exchange не создаётся.
- Повторное Kafka-событие не создаётся либо безопасно дедуплицируется.
- Новый счёт в 1С не создаётся.
- Клиент получает результат ранее выполненной операции.

Если повторное событие всё же дошло до 1С и 1С вернула `duplicate_document`, это не должно переводить ранее успешно обработанную операцию в состояние «счёт не сформирован».

Для данного `exchange_id` должен сохраняться успешный результат первого события:

```ini
invoice = inv-2026-00088234
```

А не:

```ini
invoice = N/A
```
