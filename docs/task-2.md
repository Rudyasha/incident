# Задача 2. Баг-репорт

## Summary

Созданный счёт отображается как `invoice=N/A` в реестре

## Severity / Priority

| Severity | Priority |
|---|---|
| Major | P1 |

**Обоснование:** баг затрагивает финансовый процесс: счёт фактически создаётся в 1С, но итоговый реестр показывает ошибку и требует ручной обработки. При этом есть признаки, что проблема не единичная: похожие зависания наблюдались у нескольких водителей.

## Окружение

- Lincore Driver App, React Native
- Lincore API
- Kafka, topic `lincore.orders`
- 1C Connector
- 1С:ERP
- Финансовый реестр

| Параметр | Значение |
|---|---|
| Инцидент | 24.08.2026 |
| Рейс | M-148 |
| Точка | 3, Кафе Утро |
| `exchange_id` | `ex-20260824-0010482` |

Версия приложения и backend build в предоставленных материалах не указаны.

## Предусловия

1. Водитель авторизован
2. Рейс находится в статусе `В работе`
3. Точка маршрута достигнута — 3, Кафе Утро
4. Ковры отсканированы
5. Для точки ещё не завершён обмен

## Шаги воспроизведения

1. Открыть точку маршрута в статусе `В работе`
2. Нажать `Завершить обмен`
3. Дождаться, пока первый `POST /api/v1/exchanges` успешно обработается backend:

    - exchange сохранён в БД
    - событие опубликовано в Kafka

4. Не доставить HTTP-response клиенту до истечения его timeout
5. После появления ошибки в приложении повторно нажать `Завершить обмен`
6. Убедиться, что повторный запрос отправлен с тем же `exchange_id`
7. Проверить DB, Kafka, 1C Connector, 1С и финансовый реестр

## Actual result

Первый запрос успешно обрабатывается:

- exchange сохранён в БД с `id=318274`
- Kafka event опубликован с `offset=88234`
- 1С успешно создаёт счёт `inv-2026-00088234`

После timeout клиент повторяет запрос с тем же `exchange_id`. Backend повторно:

- создаёт exchange `id=318275`
- публикует второе Kafka-сообщение `offset=88235`

1С отклоняет повторное создание документа:

```text
400: Документ с номером ex-20260824-0010482 уже существует
```

После этого событие попадает в DLQ с причиной `duplicate_document`.

В финансовом реестре точка отображается как **`invoice=N/A`**, хотя первый Kafka-event уже успешно создал счёт в 1С.

## Expected result

Повторная отправка той же бизнес-операции с тем же `exchange_id` не должна создавать второй exchange и повторно инициировать создание счёта.

Ожидаемо:

- Сохраняется одна бизнес-операция для одного `exchange_id`
- Повторный запрос возвращает результат уже выполненной операции или безопасно обрабатывается как retry
- Повторный Kafka-event либо не публикуется, либо безопасно дедуплицируется downstream
- Уже успешно созданный счёт остаётся связан с exchange
- Повторная доставка не переводит успешную операцию в ошибочное состояние `invoice=N/A`; реестр не ссылается на дублирующую запись вместо исходной операции
